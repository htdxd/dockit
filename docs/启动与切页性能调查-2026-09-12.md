# 启动与切页性能调查

日期：2026-09-12。最新结论：第三轮已在用户原启动脚本路径捕获慢启动，缩小 Vite 文件监控范围后，用户复测确认明显变快；见文末。前文保留历次调查记录，早先小样本不能代表用户实际启动情况。

用户确认：通过 `start-dockit.bat` 启动；窗口出现后，整个内容区连同侧栏空白几十秒，再显示界面。

## 结论

首屏白屏与成果数据加载应分开处理。本次未复现桌面 WebView2 的几十秒白屏，不能认定唯一根因；已确认成果页存在重复初始化、切页动画重复启动、日志全量重绘等可优化路径。

`start-dockit.bat` 调用 `npm run tauri dev`，每次进入开发启动链路。配置使用 Vite devUrl，当前 bundle.active=false；它不是针对日常使用的独立发布入口。

`index.html` 初始只有空的 #app，界面由 JavaScript 的 mountLayout 创建。mountLayout 在数据库加载、后端通信之前执行。因此，数据库或成果扫描慢可以延迟数据，却不能单独解释“侧栏也没有”的首屏白屏；应进一步测量桌面窗口创建、WebView2 导航、首个脚本执行和首帧之间的耗时。

## 已确认的优化点

## 建议顺序

1. **先定位桌面白屏**：分别记录窗口创建、WebView 导航、脚本入口、mountLayout 和首帧时间；对比当前开发启动与本地生产构建。不能把编译前的等待与窗口出现后的白屏混算。
2. **处理已确认的切页重复工作**：数据库/设置初始化一次，成果页读取现有状态，按需后台刷新。这一步不需要改动整体架构。
3. **改善过渡与重绘**：去掉父子页重复淡入，减少强制布局；仅刷新可见或发生变化的内容。
4. **改善首屏反馈**：可在静态 HTML 中提供轻量加载壳和加载失败提示，避免全白。它改善反馈，实际启动耗时仍需按测量结果处理。
5. **提供日常启动方式**：验证生产构建可用后，再提供不依赖开发服务器的启动入口；保留开发脚本供改代码使用。本轮未编译或切换桌面发布版本。

性能调查仅启动本地 Vite 和临时浏览器测量页，未修改应用性能代码、数据库配置或用户资料；未调用文档生成工具、外部模型或 MinerU API。测量页和 Vite 已关闭，临时测量监听随页面关闭而移除。

已实施：

- 入口先加载 UI 与样式，绘制完整真实界面，再加载控制器、原生 API 和设置。初始化期间可浏览页面、填写任务内容，上传/生成/设置等尚未就绪的操作暂时禁用；失败时给出提示。

## 第三轮：用户原脚本启动的根因与复测

用户后续连续两次报告 14–16 秒空屏，与测试样本不符。本轮让原 start-dockit.bat 自动记录真实启动，避免再次用额外测试实例替代用户路径。

实际慢启动 PID 52456 的记录：HTML 约 542 ms 返回，但 /src/main.ts 请求耗时 58,018.5 ms，无 imports 的 Vite env.mjs 也等待 55,520.4 ms；两者几乎同时完成。随后 UI/CSS 只需 19–25 ms，mountLayout 约 3 ms，Python 子进程创建约 14 ms。它排除了本次等待由模板排版、SQL 设置或界面挂载耗时直接造成的解释。

关键问题是 Vite 的文件监控范围：原设置监控整个项目约 15,092 项文件/目录资源，其中包括大量后台 PPT 模板与 ResumeCollection，实际进程句柄数约 15,354。初始监控登记仍在后台推进时，正常启动脚本已打开应用，首轮文件请求被拖延。早先独立测试的请求时机避开了这一繁忙段，因此结果不能外推。

修复：Vite 仅监控 src、public、应用入口、包清单、Vite 配置及根目录环境配置。后端代码、模板原件、输出、测试证据等不再由前端开发服务器监控。独立检查中监控项降到 33，真实运行进程句柄降到 295；仍保留前端及配置热更新，没有关闭全部文件监控。
