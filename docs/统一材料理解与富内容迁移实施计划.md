# 统一材料理解与富内容迁移实施计划

## 1. 文档状态与执行规则

- 状态：规划草案，等待用户在对话中明确确认“计划完成”。该确认消息即为冻结信号，无需再修改状态字段。
- 基线提交：`4b23b14`（能力探测指纹与 Qwen 探测兼容性修复）。实施前必须用 `git log -1 --oneline` 核实，不得假设工作区仍处于该提交。
- 本文面向新对话中的实现 Agent。用户确认计划完成后，本文在执行阶段视为只读；遇到计划外冲突时必须报告问题、提供选项并取得用户确认，才能进入反馈阶段修改本文。
- 本计划不启用多 Agent。后续只有用户明确授权后，才可以补充多 Agent 的职责、读写边界和交接协议。
- 实施必须按阶段顺序推进。每一阶段满足自己的测试门和验收条件后才能进入下一阶段，禁止把四个 Skill 同时改到不可运行状态。
- 所有代码、测试和文档响应遵守仓库级 `AGENTS.md`（若存在）及用户级工程规范；Python 命令使用项目虚拟环境和 `uv run`。

## 2. 目标

为 PPT 生成、简历生成、DOCX 生成和 PDF 转 DOCX 建立一套共享的材料理解与富内容迁移能力，使 Agent 能够：

1. 读取用户上传材料中的正文、标题、列表、图片、表格、公式、代码和必要的版式关系；
2. 判断哪些内容与当前任务相关，明确选择或舍弃，并保留来源证据；
3. 把选中的内容放入输出产物中的合适章节、页面或模板组件；
4. 由确定性程序完成 OOXML/SVG/PPTX/DOCX 操作和硬约束检查；
5. 有 Vision 时进行视觉选择与渲染复核，无 Vision 时走保守、可解释、可机械验证的降级工作流；
6. 对精选简历模板支持受约束的组件扩展、平移和复制，同时尽量保持原模板观感。

产品目标不是任意文档的像素级复刻，而是：

- 对精选模板和常见材料稳定地产出高质量、可继续编辑的文件；
- 对复杂或任意模板保守处理，明确未验证项，不伪造质量结论；
- 让四个功能复用同一份材料事实、资源目录、选择计划和质量状态，而不是各自重复解析。

## 3. 已确认约束

### 3.1 MinerU

- MinerU 是本阶段四个功能的强依赖。每个任务启动前都必须执行统一 preflight；MinerU 不可用时任务直接失败，不进入 Agent loop。
- 本阶段不设计其他 OCR/视觉解析服务 fallback，也不允许某个 Skill 在 MinerU 失败后自行切换到另一条隐式路线。
- “无 fallback”不等于四个 Skill 直接耦合 MinerU。MinerU 必须封装在共享 `MaterialUnderstandingService` 的 adapter 后，Skill 只消费稳定 IR。
- ParserRouter 仍可为 DOCX、Markdown、TXT、PPTX 使用原生解析器，以保留 OOXML、样式和关系；但 MinerU preflight 仍是全局任务门槛。选定 MinerU 路由后若转换失败，任务失败。
- 对需要同时保留可见内容和原生结构的 DOCX/PPTX，可采用双通道：原生结构解析 + 渲染副本/MinerU 视觉解析，再按 provenance 合并，不能用 MinerU Markdown 覆盖原生结构事实。
- 上传材料会按所选 MinerU 服务协议发送给第三方，前端必须在任务开始前持续展示这一事实；日志不得写入 Token。

### 3.2 Agent 与确定性程序的边界

- Agent 负责语义理解、资源选择、内容规划、受限布局决策和质量结论解释。
- Vision Agent 可以读取候选资源和源/目标渲染图，负责图片角色判断、相关性判断、视觉布局建议和渲染复核。
- Agent 不得直接任意改写 DOCX/PPTX OOXML，不负责 relationship、ID、anchor、group transform、z-order 等结构完整性。
- Agent 只能输出经过 schema 校验的 `ContentPlan` 和 `LayoutAction`；Renderer 负责执行，Validator 负责拒绝越界、重叠、损坏或不受支持的动作。
- 机械检查失败属于硬失败，Agent 和 Vision 检查都不能覆盖；视觉检查只能补充机械检查不能判断的语义和审美问题。

### 3.3 Vision 与无 Vision

- `vision` 保持 optional capability，但必须在任务开始前解析为明确布尔值；Skill 不得自行猜测。
- `vision=true` 使用智能模式：允许读取必要的候选图片、执行自适应布局建议，并在产物渲染后进行最多 3 轮有界视觉修复；第一版不额外开发 contact sheet 管线。
- `vision=false` 使用保守模式，而不是简单跳过 `read(image)`：
  - `asset_policy=high_confidence_only`；
  - `layout_policy=conservative`；
  - `component_mutation=template_whitelist_only`；
  - `qa_policy=mechanical_only`。
- 无 Vision Agent 可以通过一次批量 `ask_user_questions` 请求用户确认高影响且无法从文本可靠推断的问题；问题应优先使用文件名、图注、相邻正文和目标 slot 描述，不要求用户理解内部 IR。
- 无 Vision 模式只在高置信度条件下自动使用图片：用户明确标注、明确图注、稳定相邻关系、明确文件名、原模板一对一 slot，或精选简历模板中高置信度头像候选。
- 中低置信度资源应询问用户或舍弃。默认优化 precision，允许牺牲 recall，禁止为了“充分利用材料”而猜测图片含义。
- 无 Vision 产物必须同时显示“结构与机械检查：已通过/失败”和“视觉版式检查：未执行”，不得声称完成视觉验证。

### 3.4 用户交互

- 用户可以只提供极少量初始指示；Agent 先利用 IR 和上下文自动规划，只追问会显著改变内容真实性、资源选择或布局的事项。
- 默认每个任务最多一次 `ask_user_questions`，一次收集所有当前可知问题。只有用户回答引入新的实质歧义时才能再问一次，并在日志中记录原因。
- 用户可以选择“跳过，按保守策略生成”。跳过后不能再次追问同一问题。
- 问题必须结构化为 `text`、`textarea` 或 `select`，继续沿用现有工具契约；若未来需要图片选择 UI，应单独扩展协议，不在本计划中暗中复用文本字段传 base64。

### 3.5 测试策略

- 本改造的测试是强制实施阶段，全部新增测试放在 `tests/` 或现有前端测试目录，不在生产源文件末尾放临时测试。
- 自动化测试默认离线：MinerU 使用 fixture/fake CLI，Provider 使用 scripted/fake provider，不发送用户文件或测试文件到第三方。
- 真实 MinerU、真实 Vision Provider 和 Office 渲染测试必须使用显式 marker/环境变量；缺少凭据或 Office 时允许跳过，但不得把跳过报告成通过。
- 每个阶段先运行高层集成测试，再运行失败子系统的聚焦测试；最终必须运行完整后端、前端和类型检查。

### 3.6 极简实现原则

- 只实现本文明确列出的四个功能、当前支持的材料格式和 5 套精选简历模板；不为未知未来格式、第三方 Skill 或任意模板预建扩展框架。
- 本文中的 Adapter、Planner、Renderer、Validator 是逻辑职责，不要求一一映射为 class、package 或独立服务。能用现有模块中的小函数清楚表达时，不新增抽象层。
- 共享材料能力最多优先拆为两个聚合模块：数据模型和材料处理；只有单文件再次明显过深时才依据实际依赖拆分，不预先建立通用 Parser 插件系统。
- 继续复用现有 `AgentRuntime`、`ToolRegistry`、Skill manifest、Prompt 和已验证脚本；不引入工作流引擎、任务队列、数据库、依赖注入容器或跨任务缓存。
- 只保留一个稳定 `DocumentIR`、一个 `ContentPlan` 和必要的 Resume 受限动作 schema；禁止同时维护多套等价 DTO 或为了兼容假想调用方增加 facade。
- MinerU 失败、schema 非法、文件损坏、模板 hash 不匹配或机械硬约束失败时直接返回明确错误；不增加多层 `try/except`、隐式重试、自动改参数或“尽力猜测”的兜底链。
- 除明确允许的最多 3 轮 Vision 布局修复外，外部命令默认不自动重试。瞬时服务重试若以后确有运行证据，再经用户确认加入计划。
- 每一阶段删除被新路径完全替代的旧逻辑，或保留一个有明确删除期限的短期兼容投影；禁止长期双写、双读和 feature flag 叠加。
- 新依赖必须证明标准库、现有依赖和已 vendored 的 ppt-master 代码无法满足；不得仅为少量 schema/调度代码引入库。
- 优先让错误显式暴露并由测试覆盖，不为理论上的异常组合编写无人使用的防御代码。

## 4. 明确不在本计划范围

- MinerU 替代服务、离线 OCR fallback、自动服务切换或降级到纯文本模式。
- 任意用户 DOCX/PPTX 模板的像素级保真承诺。
- 内置 Office/PPT/DOCX 编辑器、通用 Chatbot、任意 Skill/MCP 市场。
- 网络图片搜索、AI 图片生成和与用户材料无关的补图。
- 自动修改原始上传文件；所有变换只能作用于任务 workspace 中的副本。
- 同一产物在 Word、WPS、LibreOffice 和不同字体环境中完全一致的保证。
- 跨任务长期材料缓存。本阶段只做任务内按内容 hash 去重与复用，避免隐私和失效策略扩张。
- 通用 Parser 注册中心、可热插拔 adapter、后台任务队列、分布式 Material Service、自动扩缩容和持久化作业恢复。
- 自动编译任意简历模板；本阶段只增强 5 套精选模板的 manifest 和执行脚本。

## 5. 当前实现基线与已知缺口

实施 Agent 必须先验证以下结论是否仍成立；若代码已变化，以当前源码为准并进入反馈阶段，不得机械套用旧行号。

- `runtime.py` 负责暂存上传文件、注入 `[MATERIALS]` 横幅和 Agent tool-call loop。
- `tools.py` 的当前 IR 是 Markdown + media + manifest，缺少 block 级页码、bbox、父子关系、caption、样式和 provenance。
- 当前 DOCX ingest 只提取普通段落、简单表格和媒体清单，会丢失标题层级、列表、OMML 公式、复杂合并单元格和图片原始位置关系。
- 当前 staging 以 basename 平铺文件，Markdown 相对资源目录、同名文件和同 stem 文件存在碰撞风险。
- 当前小文件自动 ingest 在进入模型循环前同步执行；MinerU 和 Office 长任务可能阻塞事件循环。
- Runtime 当前默认工具超时约 90 秒，而 MinerU 脚本内部允许约 1800 秒，外层可能提前终止正确任务。
- MinerU Token 当前仅路由到 PDF Skill；共享材料服务必须取得受限凭据，但不能把 Token 暴露给所有 Skill 脚本。
- PPT Skill 仍带有独立 `source_to_md` 解析链；它的成熟解析能力应复用为共享 adapter，而不是与 Runtime IR 并行产出两套事实。
- DOCX 生成规格把 tables/images/formulas 作为全局尾部数组，不能表达“在某一段后插入资源”。
- `apply_template.py` 当前清空模板正文再注入纯文本结构，不是语义 slot 填充，不能承诺保留正文美化组件。
- `resume_pro` 当前是 L1 原位文本替换和头像字节替换；Prompt 明确禁止几何变换，溢出主要依赖删减文本。
- PDF 多文件转换可能从共享目录选错 `.docx`；多个渲染任务复用 `page-1.png` 前缀可能污染结果。
- PDF 失败 Prompt 与 `finish_task` 只接受成功 artifacts 的工具契约冲突；失败应通过 `task_failed` 结束，不应伪造说明型 artifact。
- PPT/PDF manifest 必须复核 `tool_calling` required capability；所有四个 Skill 都依赖工具调用推进任务。
- 当前测试已覆盖基础 Runtime、ingest、照片替换和 DOCX 生成，但没有完整覆盖四功能共享富媒体闭环、真实多文件隔离、Vision/无 Vision 双路线和简历组件变换。

实施前基线命令：

```powershell
git status --short --branch
git log -5 --oneline
uv run pytest tests/ -q
npm test
npx tsc --noEmit
```

若基线测试失败，先区分既存失败与本计划相关失败；未经用户确认不得把修复无关既存问题扩大进本计划。

## 6. 目标架构

```text
Task start
  -> DependencyPreflight (MinerU hard gate + model capability resolution)
  -> MaterialUnderstandingService
       -> task-local staging and hashing
       -> ParserRouter
            -> MinerUAdapter
            -> NativeDocxAdapter
            -> NativeMarkdownAdapter
            -> NativePptxAdapter (reuse ppt-master parser)
       -> IRMerger
       -> DocumentIR + AssetCatalog + page renders
  -> Agent Material Planner
       -> optional batched ask_user_questions
       -> ContentPlan
  -> Skill-specific Renderer
       -> validated LayoutAction DSL
       -> artifact candidate
  -> MechanicalValidator
  -> Office/PDF renderer
  -> optional VisionQA
  -> bounded repair loop
  -> publish versioned artifact + QAReport
```

职责边界如下。它们是代码责任边界，不代表必须创建六个 class 或六个文件：

| 模块 | 唯一职责 | 禁止承担 |
|---|---|---|
| DependencyPreflight | 验证 MinerU 和模型能力，生成执行模式 | 解析材料、调用 Agent |
| MaterialUnderstandingService | 解析、合并、缓存任务内材料事实 | 决定业务相关性、排版产物 |
| Material Planner | 选择内容并生成可审计计划 | 直接写 OOXML、绕过 schema |
| Skill Renderer | 按计划和模板约束生成候选产物 | 猜测资源含义、修改原文件 |
| MechanicalValidator | 检查结构、几何、容量、关系和文件完整性 | 做审美判断 |
| VisionQA | 判断语义匹配和视觉观感，提出受限修复 | 覆盖机械硬错误 |

## 7. Workspace 与状态所有权

每个任务使用独立临时 workspace。原始文件保持只读副本，统一目录如下：

```text
sources/
  <material_id>/
    original.<ext>
work/materials/
  manifest.json
  <material_id>/
    document.json
    content.md
    assets/
      <asset_id>.<ext>
    pages/
      page-0001.png
    native/
      source-map.json
work/plans/
  content-plan.json
work/qa/
  mechanical-report.json
  vision-report.json          # 仅 vision=true 时存在
artifacts/
  <candidate/final files>
```

- `material_id` 由源文件 SHA-256 和安全化扩展名构成，建议使用完整 hash 存 manifest、前 16 位作目录名；发生前缀冲突时扩展长度。
- `asset_id` 由材料 ID、来源 locator 和资源内容 hash 派生，不能只使用原始文件名。
- manifest 和所有对 Agent 暴露的路径必须是 workspace 相对路径，禁止写入临时绝对路径。
- 同一源文件在当前任务内只解析一次；缓存命中必须同时校验 schema version、解析状态和必需产物存在。
- 每个材料拥有独立 `assets/` 和 `pages/`，禁止共享 `_media/` 或 `page-*.png` 名称空间。
- Runtime 拥有 MaterialUnderstandingService 生命周期；Skill 只获得只读 catalog/tool view，不拥有解析缓存。

## 8. 最小数据契约

数据模型建议放在 `backend/skill_toolbox/material_models.py`；材料处理优先集中在 `backend/skill_toolbox/materials.py`。只有实现过程中证明单文件无法清晰维护时才继续拆分。

### 8.1 DocumentIR

使用 Pydantic 定义版本化 JSON。第一版只包含当前工作流真正消费的字段：

```text
DocumentIR
  schema_version: "1"
  material_id: str
  original_name: str
  source_format: pdf | docx | md | txt | pptx | image
  sha256: str
  page_count: int | null
  blocks: list[Block]
  assets: list[Asset]
  warnings: list[str]

Block
  id: str
  type: heading | paragraph | list | table | formula | code | image | page_break
  order: int
  text: str
  level: int | null
  page: int | null
  bbox: [x, y, width, height] | null
  parent_id: str | null
  caption: str | null
  asset_ids: list[str]
  source_locator: str

Asset
  id: str
  path: str
  mime_type: str
  sha256: str
  width: int | null
  height: int | null
  page: int | null
  bbox: [x, y, width, height] | null
  caption: str | null
  surrounding_text: str
  source_locator: str
```

约束：

- `bbox` 使用页面归一化坐标 `[0,1]`；原生 EMU/twip 等只保留在 `source_locator` 指向的 native sidecar 中，不污染跨格式 IR。
- `source_locator` 是可审计定位字符串，例如 `docx:word/document.xml#p[12]`、`pdf:page=3:block=7`；第一版不定义通用 locator 解析器。
- 表格正文在 `text` 中使用稳定 Markdown 表格投影；复杂合并关系若 Renderer 需要，保存在该材料的 `native/source-map.json`，不扩张 Block schema。
- 公式 `text` 保存可编辑 LaTeX/线性表达；无法可靠转换时保存原始可见文本并追加 warning，不伪造公式结构。
- 图片 block 必须通过 `asset_ids` 保留原始位置关系；不能像当前实现一样只在材料级列出媒体。
- `content.md` 由 DocumentIR 投影生成，供 Agent 顺序阅读；它不是事实真源，不能反向解析覆盖 `document.json`。
- schema 解析只要求兼容同一 `schema_version`；不为不存在的历史 V2/V3 编写迁移逻辑。

### 8.2 ContentPlan

Agent 必须先写 `work/plans/content-plan.json`，Renderer 不直接从对话文本猜测材料选择：

```text
ContentPlan
  schema_version: "1"
  task_type: ppt | resume | docx | pdf_to_docx
  mode: vision | conservative
  selections: list[Selection]
  exclusions: list[Exclusion]
  questions_asked: bool

Selection
  source_id: block_id | asset_id
  purpose: str
  target: str
  transform: preserve | summarize | crop | table | formula

Exclusion
  source_id: block_id | asset_id
  reason: irrelevant | duplicate | low_confidence | unsupported | user_rejected
```

- `target` 使用各 Skill 已知的简单定位：PPT 为 slide intent，DOCX 为 section/block slot，Resume 为 manifest component/slot；本阶段不发明跨产物统一坐标语言。
- 每个被读取并具有迁移价值的 Asset 必须出现在 selections 或 exclusions 中，便于解释遗漏；纯装饰和低价值小图可在材料阶段统一标为 warning 后不进入候选集。
- Agent 输出不增加浮点“相关性分数”。第一版只使用明确选择、舍弃理由和无 Vision 高置信度规则，避免伪精确排序系统。

### 8.3 QAReport

```text
QAReport
  mechanical: passed | failed
  mechanical_issues: list[str]
  visual: passed | failed | not_run
  visual_issues: list[str]
  repair_rounds: int
  used_assets: list[str]
  skipped_assets: list[str]
```

QAReport 写入任务日志并作为前端状态来源，不要求作为独立用户产物发布。

## 9. 共享材料工作流

### 9.1 Preflight

在 Sidecar 接受 `start_task` 后、创建 Provider/AgentRuntime 前执行：

1. 检查 `mineru-open-api` 可执行入口能否解析；
2. 检查设置页 MinerU Token 已配置；
3. 校验 Skill 的 `tool_calling` required capability；
4. 解析 `vision` 为明确布尔值并生成 `vision`/`conservative` mode；
5. 失败时发送一个结构化 `task_failed`，包含稳定错误码和面向用户的恢复说明。

第一版错误码只定义实际需要的集合：

```text
MINERU_CLI_MISSING
MINERU_TOKEN_MISSING
MINERU_PARSE_FAILED
MODEL_TOOL_CALLING_REQUIRED
MATERIAL_UNSUPPORTED
MATERIAL_CORRUPT
```

不要为每种 subprocess stderr 创建错误类型；原始错误截断后写调试日志，前端使用稳定错误码和简短说明。

### 9.2 暂存与解析

1. Sidecar 校验用户路径确为文件，Runtime 计算 hash 后复制为 `sources/<material_id>/original.<ext>`。
2. 同 hash 材料只保留一份，并在 manifest 记录多个原始名称；不同目录的同名文件不得覆盖。
3. 按当前明确格式路由：
   - PDF：MinerU 为主，生成 Markdown、media、页码/bbox（若输出提供）和页面渲染；
   - DOCX：原生 OOXML 提取结构与关系；复杂可见版面需要时渲染为 PDF 后调用 MinerU，再合并可见 block；
   - Markdown/TXT：暂存前从原文件父目录解析并复制安全的相对引用资源；拒绝 `..` 越界和远程 URL，无法找到的引用产生 warning；
   - PPTX：复用 ppt-master 当前 `ppt_to_md`/intake 中实际需要的解析函数，不复制整套 workflow；
   - 独立图片：只登记 Asset；Vision 模式可读，无 Vision 模式按文件名、用户说明和目标 slot 判断。
4. 写 `document.json`、`content.md`、assets 和任务级 manifest。
5. 解析完成后才进入 Agent loop；通过事件向前端报告当前文件和进度。

不为解析建立后台队列。实现使用当前 asyncio 流程加 `asyncio.to_thread`/受控 subprocess，确保 Sidecar 消息循环可响应取消即可。

### 9.3 合并规则

- 原生结构事实优先：段落层级、OOXML relationship、表格结构和模板组件来自 Native parser。
- 可见内容事实补充：OCR 文本、扫描页内容、页面 bbox 和 MinerU 媒体来自 MinerU。
- 仅按明确 locator、页码顺序、资源 hash 和相邻文本合并；无法确认的项并列保留并写 warning，不实现模糊图匹配算法。
- 同一媒体 hash 重复出现时保留一个 Asset 和多个 block 引用。
- 合并逻辑保持线性遍历和字典索引，禁止为 block 配对引入 O(n²) 全量比较。

### 9.4 Agent 工具

在现有工具集上做最小扩展：

- 保留 `read`、`write`、`edit`、`exec_cmd`、`ask_user_questions` 和 `finish_task`。
- 将现有 `ingest` 改为 Runtime 预处理后的只读查询或内部兼容入口；Agent 不应重复触发解析。
- Runtime 横幅列出材料摘要、`document.json`、`content.md` 和候选 Asset 路径；Agent 继续通过现有 `read` 分页读取 IR/Markdown 和 Vision 图片，不新增 `list_materials` 工具。
- `read` 禁止向 Agent 返回绝对路径。
- 不新增通用 SQL、shell、文件遍历或任意 OOXML 编辑工具。

### 9.5 超时、取消与失败

- 普通读写工具沿用短超时；MinerU、Office 渲染和 PPT 导出按 action 设置显式长超时。优先在 Skill manifest script spec 增加可选 `timeout_seconds`，不建立独立调度系统。
- Runtime 外层超时必须大于或等于脚本内部超时加小量清理余量，禁止出现当前 90 秒外层终止 1800 秒 MinerU 的情况。
- 取消任务时终止当前子进程及其直接进程树，清理临时 workspace；Office COM 脚本必须在 `finally` 中关闭文档和应用进程。
- 解析或生成失败直接返回 `TaskResult(status="failed")`；`finish_task` 仍只发布成功且存在的 artifact，不扩展 `error` 参数。
- 默认不自动重试外部命令。Vision 修复循环只处理已成功生成候选后的布局问题，不重试 MinerU/认证/文件损坏错误。

## 10. 四个功能的目标工作流

四个 Skill 的 Prompt 都必须先读取 Material summary，再写 ContentPlan，最后调用各自 Renderer。Prompt 只描述决策规则，不复制 Material parser 的实现细节。

### 10.1 PPT 生成

```text
shared ingest -> ContentPlan(slide intent + selected blocks/assets)
-> existing ppt-master project/SVG route
-> svg quality gate -> PPTX export -> QAReport
```

- 把 ppt-master 中成熟的 DOCX/PDF/PPTX 材料解析能力下沉或调用到共享材料层；PPT Prompt 不再另跑一份 `source_to_md` 产生第二套事实。
- Generate 路由根据 ContentPlan 把图片、表格和公式放入明确 slide intent；每个 SVG 资源引用必须能回溯到 Asset ID。
- Fill 路由只填充原 PPTX 可识别 slot。无 Vision 时禁止自由裁剪和无 slot 的浮动图片布局；必要时用一次 `ask_user_questions` 让用户选择资源与页面用途。
- 继续复用现有 `svg_quality_check`、`finalize_svg`、`svg_to_pptx`，不重写 ppt-master 导出器。
- Vision 模式读取关键页渲染进行复核；无 Vision 模式只运行 SVG/PPTX 结构、边界、字号、资源和文本容量检查。

### 10.2 DOCX 生成

```text
shared ingest -> ContentPlan(section/block target)
-> interleaved document spec -> existing docx_pro builder
-> postcheck -> render -> optional VisionQA
```

- 把当前 `sections + tables + images + formulas` 尾部数组改为最小的顺序 block 列表，使图片、表格、公式可出现在指定 section 和段落之间。
- Builder 复用现有 CJK、封面、表格、图片、公式、目录和页码 helper；只增加顺序 dispatch，不新建第二套 DOCX engine。
- 模板模式第一版只保留模板的 sections、header/footer 和 styles，并填入明确 slot；不能识别 slot 的上传模板直接失败并建议用户显式改用非模板模式，不能自动回退或声称保留全部装饰。
- 无 Vision 时只使用有图注/明确上下文的 Asset，采用单栏、居中、保持比例的保守布局；歧义资源批量询问用户或舍弃。
- 机械门必须覆盖包完整性、关系、图片边界/比例、表格跨页规则、页数、空白页和占位符泄漏。

### 10.3 PDF 转 DOCX

```text
preflight -> isolated MinerU conversion per PDF
-> audit -> Office render -> optional VisionQA -> publish
```

- 每个 PDF 使用独立 material/artifact 子目录和唯一输出路径；只能选择本次 MinerU 调用明确返回的文件，禁止 glob 共享目录中的第一个 `.docx`。
- `inspect_pdf` 应抽样首、中、末页或使用 MinerU 返回的文档信息，不能仅凭第一页决定整份文档；保持实现简单，固定最多 3 页样本。
- 每个文档使用独立 PNG 前缀或目录，渲染前清理该文档自身旧输出，禁止跨文档残留。
- Vision 模式检查关键页面；无 Vision 模式只报告审计、页数、媒体/表格/公式残留风险和“视觉检查未执行”。
- 转换失败走 `task_failed`，不调用 `finish_task` 伪造错误 artifact。

### 10.4 简历生成

```text
shared ingest -> resume fields + selected assets
-> curated template LayoutManifest
-> whitelisted component actions
-> fill candidate -> mechanical checks -> render -> optional VisionQA
```

- 继续限定现有 5 套精选模板，不实现任意模板自动编译。
- 原简历 DOCX 的文本和图片由共享 IR 提供；模板自身始终从原生 OOXML 读取，不能经过 MinerU 后再写回。
- 支持头像以及与具体项目有明确关联的结构图；结构图只有目标模板声明 media slot 或允许的 component action 时才嵌入。
- Vision 模式可查看头像/结构图候选和产物页面；无 Vision 模式优先用用户单独上传、明确图注、文件名和原位置关系，仍不确定时通过一次 `ask_user_questions` 让用户选择或跳过。
- 内容不足时保留/删除模板示例必须遵守用户选择；不得把模板示例内容当成用户事实。

## 11. 简历受限版式能力

### 11.1 LayoutManifest

在现有每套模板 manifest 中增加最少的组件信息，而不是建立运行时通用模板编译器：

```text
template_sha256
components[]:
  id
  objects[]              # 现有 anchor/wsp 或稳定 OOXML selector
  bbox_pt
  content_slot
  allowed_actions[]
  moves_with[]
  min_height_pt
  max_height_pt
```

- 索引脚本可离线更新 manifest，但运行时只读取已经审核的 manifest。
- `template_sha256` 不匹配时立即失败并提示重新索引，禁止对未知结构继续套用旧 selector。
- `moves_with` 只描述当前 5 套模板实际需要同步移动的装饰线、背景块、标题和正文框，不抽象为通用约束求解器。

### 11.2 允许动作

第一版只允许以下动作：

```text
replace_text(component, value)
replace_asset(slot, asset_id | remove)
resize_component(component, height_pt)
shift_components(component_ids, dy_pt)
clone_component(component, after_component)
```

- 每个动作必须在模板 manifest 的 `allowed_actions` 中出现。
- `clone_component` 必须原子复制该组件列出的全部对象，并重写所需唯一 ID/relationship；不复制 section、header/footer 或未列出的相邻对象。
- `resize_component` 只改变 manifest 标注的可拉伸对象；若背景块和文字框必须同步，二者都应属于同一 component。
- `shift_components` 只允许纵向移动明确列表，不能让 Agent传任意 XPath 或 XML。
- 动作执行到 workspace 候选副本；任一步失败则丢弃候选，不在半修改文件上继续。

### 11.3 机械与视觉闭环

- 机械检查使用 manifest bbox、页面边界、最小间距、文本容量和 OOXML package 校验，拒绝已知重叠/越界。
- 优先使用 Word 原生布局/渲染得到的页数和文本容量信息；保留当前字符估算作为生成前预警，不作为最终通过依据。
- Vision Agent 同时读取无标记真实渲染图和带 component ID/bbox 的调试图，只能返回上述动作。
- 每轮修复重新从最后一个机械通过的候选生成；最多 3 轮。若用户此前明确选择了“压缩内容”，可执行一次保守压缩；否则仍未通过就明确失败，禁止临时发明兜底策略。
- 无 Vision 模式不运行调试图复核，只执行 manifest 白名单动作和机械门；无法确定结构图/组件复制是否合适时询问或舍弃。

## 12. Runtime、协议与前端改造

### 12.1 Runtime/Sidecar

- `TaskRequest` 增加解析后的 materials catalog 路径或对象引用；不要把完整 IR 全量塞入 system prompt。
- `_materials_banner` 改为读取预处理结果的短摘要，不再同步执行 MinerU。
- Sidecar 持有 MinerU 凭据并只传给共享材料调用和 PDF 转换 action；普通 Skill 脚本环境中不可见。
- Skill manifest 的 script spec 增加可选 `timeout_seconds`；缺省沿用 Runtime 默认值。
- 为四个 manifest 明确 `required_capabilities=["tool_calling"]`，`vision` 保持 optional。
- 新增最少事件：`dependency_check`、`material_progress`、`qa_status`；不要为每个内部函数创建 UI 事件。
- Debug JSONL 记录 material ID、parser、缓存命中、ContentPlan 路径、动作、QA 状态和错误码；不记录 Token、base64 图片或完整大文档。

### 12.2 Prompt

四个 Prompt 使用同一段简短材料协议：

1. 读取 materials summary；
2. 按任务读取需要的 block/asset；
3. Vision 模式查看必要候选，无 Vision 模式按高置信度规则并在需要时批量提问；
4. 写 ContentPlan；
5. 调用 Skill action 生成候选；
6. 执行机械门和对应 QA；
7. 只有全部必需门通过后 `finish_task`。

Prompt 不应复制 IR schema 全文、ParserRouter 细节或大段失败恢复百科；工具描述和错误消息提供具体契约。

### 12.3 前端

- 启动前显示 MinerU 强依赖状态；缺 CLI/Token 时禁用开始并链接到“第三方服务”设置。
- 无 Vision 时允许继续，但在开始按钮附近显示：

> 当前模型不支持图像理解。系统仍会解析文字、表格和公式，并仅复用高置信度图片；复杂图片选择和视觉版式检查将被跳过。建议使用支持 Vision 的模型以获得更好的排版质量。

- 结果页分别显示机械检查与视觉检查状态，不能合并成模糊的“质量检查已完成”。
- 结果元数据显示已采用和因低置信度舍弃的资源数量；第一版不新增复杂资源管理页面。
- 继续使用现有澄清弹窗呈现 `ask_user_questions`；本计划不增加图片缩略图选择器。

## 14. 兼容与迁移

- 在共享 IR 和四个 Skill 尚未同时接通前，保留当前 `work/materials/<stem>.md` 读取的短期兼容投影；它必须由新 DocumentIR 单向生成。
- 禁止旧 parser 和新 parser 同时解析同一材料后各自供不同 Skill 使用。
- 四个 Skill 全部切换并通过测试后，删除旧 `_materials_banner` 自动 ingest、全局 `_media/` 和旧 manifest 写入逻辑；不要永久保留 feature flag。
- 原有 `read(.docx/.pdf/.md)` 外部工具语义尽量保持；内部改为查询已解析 IR。若必须改变返回 JSON，先更新 Tool spec、Provider 测试和四个 Prompt，再删除旧字段。
- 现有 artifacts 命名和 output directory 行为保持不变，除修复多 PDF/渲染碰撞所需的文档级子目录。
- 模板 manifest 增加 `template_sha256` 后，首次索引当前 5 套模板并纳入仓库；运行时不自动修复 hash 不匹配。

## 15. 强制测试策略

### 15.1 测试层级

| 层级 | 必测内容 | 默认是否离线 |
|---|---|---|
| 数据模型单测 | schema、路径相对化、hash ID、非法 ContentPlan | 是 |
| 材料契约测试 | PDF/DOCX/MD/TXT/PPTX fixture 到 DocumentIR | 是，fake MinerU |
| Runtime 集成测试 | preflight、一次解析复用、超时、取消、事件、失败语义 | 是 |
| Skill E2E | 同一材料分别进入 PPT/Resume/DOCX/PDF 路线 | 是，scripted provider |
| 包结构测试 | DOCX/PPTX zip、relationship、唯一 ID、媒体引用 | 是 |
| Office 渲染测试 | Word/PowerPoint 实际打开、页数、PNG 输出和资源泄漏 | 否，显式 marker |
| Vision 验收测试 | 资源选择和渲染修复 | 否，显式 Provider/fixture |
| 前端测试 | warning、preflight error、双 QA 状态、问题表单 | 是 |

### 15.2 必备 fixture

- 两个来自不同目录但 basename 相同的文件；两个 stem 相同但扩展名不同的文件。
- Markdown + 相对 `images/` 目录，以及缺失引用资源的 Markdown。
- DOCX：标题、列表、普通/合并表格、OMML 公式、正文图片、表格内图片、文本框图片和页眉图片。
- PDF：原生文本、扫描件、混合页、表格、公式、多个 PDF 同任务。
- PPTX：文本、表格、图片、图表和重复媒体引用。
- 简历：5 套模板各至少一份短内容、一份需扩框内容、一份需复制项目组件内容、头像与项目结构图。
- 无 Vision 问题路径：明确资源无需提问、歧义资源一次提问、用户选择跳过。

Fixture 应小而有针对性。禁止把大量真实用户文件或整个 ResumeCollection 加入测试仓库。

### 15.3 关键回归断言

- MinerU CLI/Token 不可用时，四个 Skill 都在 Agent loop 前以稳定错误码失败。
- 同一任务中相同 material hash 只触发一次解析。
- 所有对 Agent 返回的路径均为 workspace 相对路径，且无法逃逸 workspace。
- DocumentIR 中图片 block 能定位 Asset，表格/公式不因 Markdown 投影消失。
- Vision=false 时 Provider 不收到 image payload，Prompt/ContentPlan 使用 conservative mode。
- 无 Vision 歧义场景最多一次批量提问；用户跳过后不重复追问。
- 四个 Skill 都先生成合法 ContentPlan，再执行生成 action。
- 多 PDF 不互相移动/覆盖 DOCX，渲染 PNG 不混入其他文档页面。
- `finish_task` 不能发布 mechanical failed 或缺失文件的候选。
- Resume clone/resize/shift 后 relationship、唯一 ID、页面边界和组件 bbox 全部通过。
- Vision=false 的 QAReport 必须是 `visual=not_run`；Vision=true 不能把 mechanical failed 改成 passed。
- 前端明确区分未执行视觉检查与视觉检查通过。

### 15.4 Live 测试门


## 17. 最终验收标准

### 17.1 共享材料能力

- 四个 Skill 使用同一 Material manifest、DocumentIR 和 Asset 路径。
- MinerU 不可用时四个 Skill 在 Agent loop 前失败，前端给出可行动提示。
- 同一任务的相同材料只解析一次，不同材料和输出互不污染。
- DOCX/MD/PDF/PPTX 中已支持的图片、表格和公式保留 block 位置或明确 warning。
- Agent 对候选富内容有 selections/exclusions 记录，不能静默丢弃高价值 Asset。

### 17.2 Vision 模式

- Vision Agent 能读取选定候选，而不是把所有图片无差别塞入 context。
- 资源选择、目标位置和变换写入 ContentPlan。
- 产物通过机械门后才进入视觉门；修复动作受 schema/模板白名单限制。
- 最多 3 轮后必须成功交付或明确失败，不无限循环。

### 17.3 无 Vision 模式

- 仍能处理文字、结构化表格、公式和高置信度资源。
- 歧义资源通过最多一次批量问题确认；用户可跳过。
- 使用保守布局和模板白名单动作，不进行自由裁剪、自由浮动布局或未经确认的组件复制。
- QA 明确显示 `visual=not_run`，前端持续建议 Vision 模型但不阻止任务。

### 17.4 简历

- 5 套模板的原始字体、颜色、主要组件和装饰关系在未操作区域保持不变。
- 支持经白名单允许的扩框、纵向平移和组件复制；相关装饰与文本框原子变化。
- 头像和明确关联的项目结构图能进入声明 slot；不明确资源不会被猜测使用。
- Word 实际渲染无已知文本溢出、组件重叠、越界、断图或损坏提示。
- 任意未索引模板不进入组件变换路径，不承诺高保真。

### 17.5 工程质量

- 全部离线测试和类型检查通过；Live 测试结果如实记录通过/失败/跳过。
- 新代码遵守极简原则，无未使用抽象、长期 feature flag、重复 IR 或隐式 fallback。
- 日志不包含 Token、base64 图片、raw CoT 或完整大材料。
- 取消/超时后不残留 MinerU、Word、PowerPoint 或渲染子进程。

## 18. 预期能力与非承诺

这些是实施目标，不是当前测量值；只有建立固定 benchmark 后才能转为产品指标。

| 场景 | 目标水平 |
|---|---|
| Vision + 精选模板/常见材料 | L3，稳定产品级闭环 |
| 无 Vision + 精选模板/文字为主材料 | L2～L2.5，保守但可用 |
| Vision + 富媒体 PPT | L2.5～L3，取决于 ppt-master 实际集成测试 |
| 任意复杂 DOCX/PPTX 模板 | L1～L2，尽力处理且明确风险 |
| PDF 像素级复刻、跨 Office 引擎完全一致 | 不承诺 |

无 Vision 的粗略一次可用率目标（需 benchmark 验证）：文字为主 DOCX/PDF 80%～90%，精选简历 75%～85%，富媒体 PPT 60%～75%。这些数字不得直接写入用户承诺或 UI。

## 19. 主要风险与控制

| 风险 | 控制方式 |
|---|---|
| MinerU 外部依赖导致全功能不可用 | 启动前 fail-fast、稳定错误码、设置页明确状态；本阶段不加 fallback |
| IR 设计膨胀 | 固定最小字段，额外原生事实放 source-map，不做通用 locator/parser 框架 |
| Vision 判断不稳定 | 结构化 ContentPlan、受限动作、机械门优先、最多 3 轮 |
| 无 Vision 误用图片 | high-confidence-only、一次批量询问、默认舍弃低置信度资源 |
| 简历 OOXML 损坏 | 5 套模板白名单、template hash、候选副本、包校验和 Word 渲染 |
| ppt-master 代码体量拖累改造 | 只加共享 IR wrapper，不搬迁或重写 vendored 子系统 |
| 实施期间双路径漂移 | 兼容投影单向生成、分阶段删除旧路径、禁止长期 feature flag |
| 测试调用真实第三方泄露材料 | 默认离线 fixture，Live 仅显式开启且只用非敏感测试文件 |
